## 1. サービス概要

- アプリ名：12万分の1 — 野球人生シミュレーション
- 「12万」は、日本高野連の硬式野球部員数（2026年5月末、124,116人）を丸めた数です。「プロになる確率」ではありません（画面にも明記しています）。
- 人生を確率で丸ごと進める「80億分の1」の野球版です。

このサービスは、野球が好きな人が、ありえたかもしれない野球人生を1回数分で体験し、「その人生がどれくらい珍しいか」を統計で知って楽しめるようにするサービスです。

アイデアは、本家の規約に則ってお借りしました。規約では、プログラムや文章や絵の複製と改変は禁止、そのアイデアから自分の作品を作るのは自由とされています。なので、それらは使わず、画面の並びや配色などの見た目を参考に、すべて自分のコードで作り直しました。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけ

ポートフォリオとして公開されている個人開発のアプリの多くは、何ができるかだけでなく、なぜその技術を選んだのか、どう作ったのか、どこで詰まって何で直したのかまで、きちんと説明されています。作ったものを人に伝えるうえで、その説明が大切なことは理解しています。この README でも、できるだけそこを書くようにしました（8〜13章）。

そのうえで私は、たくさんの人に触ってもらい、届いたフィードバックで直していく体験をしてみたいと考えました。実際の現場では、多くの人に使ってもらうために、技術以外のところも重要だと考えたからです。

### 2-2. なぜそう考えたか

以前遊んでいたゲームの開発者が、「少数の開発者が長い時間をかけてバグを探すより、大勢のユーザーに一瞬遊んでもらったほうが、不具合も改善点も多く見つかる。1人では思いつかない発想も出てくる」と話していました。その一周を自分でも回してみたいと思いました。

### 2-3. なぜ野球の人生シミュレーションにしたか

「80億分の1」のように、野球でも統計を体験できたら面白いと考えました。野球が好きな人は多いので、多くの人に使ってもらえそうだと見込んだことも理由です。

## 4. 似たサービスとの違い

本家の良さである「統計を体験する」を残し、野球の育成ゲームにならないようにしました。

| 種類 | 主な楽しみ方 | 12万分の1 が大切にしたこと |
| --- | --- | --- |
| 人生シミュレーション（「80億分の1」など） | 生まれた場所から一生を確率で体験する | この楽しみ方はそのまま残し、野球に絞った。進路の分かれ道を、野球の公式の統計で決める |
| 野球の育成ゲーム | 練習や試合で選手を強くし、プロや優勝を目指す | 育成ゲームにはしない。選ぶのは進路や出来事への答えで、能力を育てて勝つことは目的にしない。多くの人生が普通の高校で野球を終えるのは、統計どおりの姿だから |
| 野球の統計・データのサイト | 数字を調べて読む | 数字を読むのではなく、1人の人生として通り抜け、最後にその人生の珍しさを知る |

一般的な楽しみ方の比較で、個々の製品を調べた結果ではありません。

統計どおりだと、何十回遊んでもほとんどが普通の高校で野球をやめて終わり、ゲームとしては物足りないと考えました。そこで、基本の確率は壊さずに、☆に応じて倍率をかける「ポテンシャルモード」を作りました。育成で強くするのではなく、「もし才能があったら」という条件で同じ統計を体験する形にしています。

- 進路や出来事は、根拠のない乱数ではなく、公開データにもとづく条件付き確率で決めます。公式の資料（高野連、全日本大学野球連盟、NPB、日本野球連盟など）を優先しました。

## 8. 懸念点と対策

### ① 直したつもりで、確率まで変わってしまう

懸念：確率で動くゲームなので、文章を1行直しただけで、その後の人生の流れが変わることがある。気づかないうちに、統計からずれていく。

対策：10万人分の人生を変更の前後で比べる「指紋」と、段階ごとの率を40万人分で測る統計のテストで、変わっていないことを確かめる（11章）。統計が動く変更は、私が承認しない限り入れないルールにした（13章）。

### ② 数字が「プロになる確率」と受け取られる

懸念：「12万分の1」や結果の珍しさが、現実の確率そのものだと受け取られる。

対策：「12万」は高野連の部員数で、プロになる確率ではないと画面に明記した。結果の珍しさは「モデル上の推定」と書き、実測・推定・仮定を区別して出典と一緒に示す（7章）。

### ③ 実在の学校や球団の名前を使う

懸念：実在の名前を、事実と違う形で使ってしまう。

対策：出典と確認日を記録できた学校・球団だけ実名を使い、選手と関係者はすべて架空にした。大会・球団・リーグの名前は「2026年10月時点のものを仮に使っている」と、人生の記録と登録証に表示する。

### ④ 個人の情報を集めてしまう

懸念：遊ぶ人の名前や遊んだ内容を、サーバーに集めてしまう。

対策：会員登録をなくし、人生の保存はブラウザの中（localStorage）だけにした。サーバーに送るのは、人生を始めたときにブラウザが作るランダムな ID 1つだけで、名前・人生の中身・IP アドレスは保存しない（15章）。

### ⑤ 無料のサーバーの上限

懸念：人生の数のカウンターは無料プランで動いていて、遊ぶ人が増えると上限を超えて止まる。

対策：実際に、公開直後に1日の読み取りの上限を超えて止まった。登録のたびに直近1分の件数を数える作りだったので、10秒ごとの集計表を読む方式に変え、1件あたりの読み取りを平均約1,000行から約7行に減らした（9章）。カウンターが止まっても、ゲーム本体はそのまま遊べる作りにしている。

### ⑥ 翻訳で人生の中身が変わる

懸念：言語を足すときに、ゲームの中の処理まで書き換えて、日本語版の人生や確率が変わる。

対策：翻訳は画面に表示するときだけ行い、ゲームの処理は言語を見ないようにした。日本語の画面と記録を基準ファイルと比べ、1文字の変化も見つけられるようにした。韓国語・繁体字中国語は、まだ母語話者に確認してもらえていない（14章）。

## 10. やってみてわかったこと

- 良いものを作るだけでは使ってもらえません。需要があっても、気づかれなければ使われません。公開直後の1時間は、いいねも人生の数もほとんど増えませんでした。
- AI で作る速さと、大勢から届くフィードバックが合わさると、改善の一周がとても速く回ります。
- 遊ぶ人が多いと、1万分の1の人生にも本当に届きます。
- どのモードが何回遊ばれたかを記録していなかったので、ポテンシャルモードが遊ばれたかは分かりません。ただ、記録のためにユーザー登録を求めていたら、遊ばれなかったと思います。
- コードを書かなくても、何を確かめるか、どこで止めるか、何を変えてはいけないかを決める仕事が残りました。価値は実装力より、課題を見つけ、使う人を理解し、決めることにあるのではないかと考えています。

## 11. 品質の守り方

確率で動くゲームなので、「直したつもりで確率まで動いてしまう」ことを一番警戒しました。

- **統計のテスト**：高校で3年間続ける率などの段階ごとの率を、調整に使っていない40万人分の人生で測り、目標の範囲に入るかを確かめます。
- **指紋**：決まった seed（乱数の種）で10万人分の人生を走らせ、1人1行の結果を基準として残しています。変更のたびに同じ10万人を走らせ直し、差が0行なら、誰の人生も変わっていません。差が出たときは、原因を1件ずつ確かめてから基準を更新します。
- **文章の基準**：日本語の画面と人生の記録を基準ファイルに残し、意図しない文章の変化を見つけます。
- **新しい文章には専用の乱数**：記録に文章を1行足すだけで乱数を1つ余分に使い、その後の人生がずれる作りだったため、新しく足す出来事や文章は、別の乱数の列を使うようにしました。
- **テスト**：Vitest で1,000件以上（66ファイル）。人生が同じ seed で再現されること、出来事が実際に起きうること（条件に合う人生で一定の割合以上起きるか）なども確かめます。
- **画面の確認**：スマホ幅（390px）と PC 幅（1280px）で、4言語それぞれ人生を最後まで進め、エラーがないことを確認します。

## 12. 技術スタックと採用理由

### 技術選定の前提

ドメイン代を除いて、無料プランの範囲で動かすことを前提にしました。そのため、ゲーム本体はサーバーを持たない静的サイトにし、サーバーが必要なのは「作られた人生の数」のカウンターだけにしました。

### 公開先

ゲーム本体は `npm run build` で作る静的なファイルだけで動くので、候補は GitHub Pages、Cloudflare Pages、Netlify などでした。Cloudflare Pages を選んだのは、これから別のアプリやサービスを公開するときにも、同じ置き場所を使い回せると考えたからです。

- 無料プランのままで、1つのアカウントに100件までサイトを作れる
- サーバーが必要な部分も、同じアカウントの Workers と D1 で作れる。このアプリでは、人生の数のカウンターがそれにあたる。GitHub Pages は静的なファイルを配信するだけなので、サーバーの処理には別のサービスを組み合わせる必要がある

実際に、カウンターは同じアカウントの中で作れました。また、独自ドメインをやめて Cloudflare が用意するアドレスに移るときも、コードとカウンターを変えずに済みました。

無料プランの条件は、2026年10月29日に公式の資料で確かめたものです。条件は変わることがあります。

### カウンターのつなぎ方の比較

| 案 | カウンターの URL | DNS の変更 | 向いている場合 |
| --- | --- | --- | --- |
| **A（採用）** | `…workers.dev`（Cloudflare が用意するアドレス） | 不要 | まず動作を確かめたい。ドメインの DNS が Cloudflare にない |
| B | `api.1in120k.com`（独自ドメイン） | 必要 | 恒久的な URL にしたい |
| C | `1in120k.com/api/…`（ゲームと同じアドレス） | 必要。ゲームも Cloudflare 経由にする | ゲームとカウンターを同じアドレスにまとめたい |

DNS の設定を変えると、ドメイン全体に影響します。DNS に触れずに済む A を選びました。ドメインをやめた今も、カウンターはそのまま動いています。

### 無料枠の見積もり

公式の料金表（2026年10月19日に確認）では、無料プランの上限は Workers が1日10万リクエスト、D1 が1日の書き込み10万行・読み取り500万行です。1人生の書き込みを約4行と見積もり、1日およそ2.5万人生までは無料で動くと判断しました。実際には、公開直後に読み取りの上限を先に超えました（8章⑤、9章）。

### 採用技術

| カテゴリ | 技術 | 選んだ理由・使い方 |
| --- | --- | --- |
| フレームワーク | React 19 + Vite | 既存の React + TypeScript + Vite のプロジェクトから始めた |
| 言語 | TypeScript | 型があることで、AI が書いたコードの間違いに気づきやすい |
| テスト | Vitest | ロジックと統計のテスト、指紋と文章の基準の比較 |
| 画面の確認 | Playwright（確認用スクリプト） | 各言語で人生を最後まで進める通しプレイ、スマホ幅の表示崩れの確認 |
| 公開 | Cloudflare Pages | 静的サイトとして無料で配信。保存はブラウザの localStorage だけで、サーバーを持たない |
| カウンター | Cloudflare Workers + D1 | 「作られた人生の数」だけはサーバーが必要なため。無料プランで動かしている |
| 開発 | Claude Code | 実装はほぼ Claude Code が担当（13章） |

コードの量（2026年10月29日時点）：アプリ本体 約49,000行、テスト 約15,700行（TypeScript）。翻訳する文章は約8,800件です。

## 13. AI（Claude Code）を活用した開発

コードはほぼ Claude Code が書きました。私の役割は、何を作るかを決めること、報告を読んで進めるか止めるかを判断すること、そして公開してよいかを決めることでした。

### 自分で考え、判断したこと

- **何を作るか**：「80億分の1」の野球版にする。分母は高野連の部員数にして、プロになる確率ではないと明記する。
- **方向性**：試作を触って面白くないと感じたとき、本家を触っても同じ感想だったので、方向を変えずに進めると決めた。
- **ポテンシャルモード**：統計どおりだと物足りないので、基本の確率を壊さずに☆で倍率をかける形を考えた。
- **公開のタイミング**：完成度と早さのどちらを取るか迷い、自分が満足した段階で公開した。
- **何をどう直すか**：届いたフィードバックのうち、どれをどう直すかを決めた。たとえば、トレードで球団が変わっても有効な契約は新しい球団に引き継ぐ。プロポーズのやり直しは、おまかせに逆らって待ったときだけに絞る。
- **止める判断**：統計が動く変更は承認制にした。修正の範囲が広がったときは途中で止め、差分の説明を求めた。

### AI に任せたこと

- アプリの実装とテスト
- 公式ページからの統計・学校・球団の一覧の取り込み
- 指紋や統計のテストなど、確率が変わっていないことを確かめる仕組み
- 英語・韓国語・繁体字中国語への翻訳と、その抜け漏れを見つけるテスト
- カウンターの設計、無料枠の調査、公開の手順の提案
- 障害の原因の調査（カウンターが止まったときなど）

AI の報告はそのまま受け入れず、統計が動いていないか、範囲が広がっていないかを確かめてから進めました。

### 決めていたルール

- 決めた範囲の中は細かい確認で止めずに進め、段階の最後にまとめて報告してもらう
- ファイルの削除・上書き、本番への公開、承認済みの仕様の変更、指紋の基準の更新は、必ず先に聞いてもらう
- 根拠のない確率の変更をしない。結婚が増えるなど統計が動く変更は、私の承認なしに入れない
- 飛ばした検証は、報告に「未検証」と書いてもらう
- 計画書（PROJECT_PLAN.md。このリポジトリには含めていません）に決定事項と作業の記録を残し、セッションが途切れても新しいセッションに読ませて引き継ぐ

### つまずいたこと

- コマンドを実行するたびに確認が出て、作業が止まりました。コマンドの文字が少しでも違うと別物として扱われていたので、同じ名前・同じ引数で呼べる固定のスクリプトにまとめました。
- 文章の食い違いの修正が、計画の5ファイルから13ファイルに広がりました。そこで止めて、差分と範囲外の変更の一覧を出してもらってから進めました。

## 14. 未対応のこと

- 韓国語・繁体字中国語は、まだ母語話者に確認してもらえていません。
- ゲームの中の失業給付が、実際には支払われていません。直すと貯金や生涯年収の数字が動くため、判断を保留しています。

## 15. データベース

ゲーム本体はデータベースを使いません。人生の保存はブラウザの localStorage だけです。

カウンター（Cloudflare D1）は、次の3つの表だけです。名前・IP アドレス・人生の内容は保存しません。

| 表 | 中身 |
| --- | --- |
| `lives` | 人生を始めたときにブラウザが作るランダムな ID と時刻（同じ ID は1回だけ数える） |
| `counter` | 人生の数（`lives` に新しい ID が入ったときだけ1増える） |
| `rate` | 10秒ごとの登録数の集計 |

## 16. ローカルでの動かし方

必要なもの：Node.js（開発は v24 で行っています）

```
npm ci
npm run dev      # 開発サーバー
npm test         # テスト（時間がかかります）
npm run lint
npm run build    # dist/ に静的サイトを作る
```

人生の数のカウンターは、ビルド時に `VITE_COUNTER_URL` を渡したときだけ動きます（`.env.example` を参照）。渡さなければ通信せず、人数も表示しません。カウンターの詳細は `counter/README.md` にあります。

このリポジトリでは偏差値のデータを空にしているため、次の点が本番と異なります。

- ビルドしたゲームでは、偏差値が表示されず、受験の難しさはゲーム上の仮定の値で決まります
- テストは 1,228件中 1,215件が通ります。通らない13件のうち12件は、偏差値のデータを使うテストと、その影響で結果の分布が変わるテストです。残りの1件（`cohort.test.ts` の再現性）は、負荷が高いと時間切れになることがある既知のテストです

主な構成：

```
src/
  engine/          人生を進める処理（確率、進路、出来事、海外の人生）
  data/            統計・学校・球団などのデータと出典、更新履歴
  ui/              画面（タイトル、人生の画面、決断、結果、統計のページ）
  game/            途中保存、共有、人生の数の表示
  i18n/            4言語の文章と、表示するときの翻訳
  worker/          同じ条件の人生をまとめて計算する処理（画面を止めないため別スレッド）
counter/           人生の数のカウンター（Cloudflare Workers + D1）
scripts/           統計の調整や画面の確認などの作業用スクリプト
en/ ko/ zh-tw/     各言語のページの入り口
```

## 17. バージョンと更新履歴

- タイトル画面の右下の `Ver. x.y.z` を押すと、更新履歴が開きます。
- 番号と履歴は `src/data/changelog.ts` の1か所だけで管理しています。画面の番号は履歴の先頭から自動で決まります。
- 本番に公開するときは、ビルドの前に先頭へ1件追加します。機能追加はマイナー（1.0.0 → 1.1.0）、小さな修正はパッチ（1.1.0 → 1.1.1）を上げます。`date` は実際に公開した日（日本時間）で、推測では書きません。
- `src/data/changelog.test.ts` が、並び順・番号の上げ方・日付を確かめます。
